## Publication

`docs/RELEASING.md` governs. The release is committed, the tag `v0.39.40` is
pushed on the reviewed tree, and a GitHub Release is created from that tag
(not a draft, not a pre-release). `.github/workflows/publish.yml` verifies the
tag equals `package.json`'s version, re-runs the complete `release:check` in
CI, and only then runs `npm publish --provenance --access public`. The npm
registry remains the publication authority; a tag and a commit are not proof
that the package was published.

**Why the registry receipt is not in this commit.** The registry can only
serve 0.39.40 after the tagged commit is published, so a tracked registry
receipt would necessarily be committed *after* the tag — which would make the
tag and `HEAD` different commits. The release verification contract asserts
`git rev-parse v0.39.40^{commit}` equals `HEAD` and the remote tag, i.e. the
tag sits on the reviewed, tested tree. The registry receipt is therefore
recorded in the GLLA journal and the terminal summary rather than in the
tracked tree, and `npm view pi-goal-list-loop-audit version dist-tags.latest`
is the independent check.
