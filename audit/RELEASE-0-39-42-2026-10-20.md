## The 0.39.41 candidate, and why this release is 0.39.42

The 0.39.41 candidate was cut, tagged and published as a GitHub Release, and
then withdrawn before it reached npm. Its release contract failed on exactly
one gate — `check:inventory`, which rejected a generated line count that was
stale by 47 lines because the gate fix's last edits to
`scripts/host-contention.mjs` and `scripts/run-tests.mjs` landed after the
previous regeneration.

The **full test suite was green in that CI run**: 4208 pass, 1 skip, 0 fail
across 460 files, exit 0, in 803s on GitHub's runner. The inventory was the
only failing gate.

The remote tag is protected, so `v0.39.41` could not be moved to the
corrected commit, and a tag that fails its own gate can never be published by
the workflow. npm never received 0.39.41, so this release carries the
identical content — the completion-audit recovery fix and the load-aware
release gate — with the inventory regenerated, as **0.39.42**.

## The gate defect this release fixes

The release gate is a wall-clock contract: the suite's waits end in deadlines,
and bun bounds every test individually. That only distinguishes "slow" from
"hung" if the process gets the CPU the deadlines assume.

It did not get it. The maintainer workstation for this release runs 44
concurrent users — an ffmpeg render, vite builds, six other test suites — and
the session is pinned to **one of sixteen cores** (`nproc: 1`). A busy-loop
probe measured the process at roughly a quarter of a core: 11.2s of wall time
for 3.0s of CPU. A wait that needs 2.5s of CPU could take 12s of wall time
while the condition it is waiting for approached normally, and the deadline
fired and reported a healthy system as broken.

The numbers, measured rather than assumed:

- The default per-test budget was 60s; the slowest legitimate test that
  relies on it takes 22.8s (`tests/goal-timeline.test.ts`). That is 2.6x of
  headroom, and the test was killed by bun's own timeout on a contended host.
- A `/glla fleet` scan has a 2s wall ceiling. Under load its first async open
  could not be scheduled inside the budget, the deadline fired, and a healthy
  project was reported with no status and an incomplete report — a false
  negative from a read-only diagnostic.
- Fifty wait deadlines were hand-rolled across 38 test files, each a fixed
  wall-clock number with no shared notion of a hang budget.

### The fix

`scripts/host-contention.mjs` measures the discrepancy directly: it runs a
short CPU-bound probe and compares the wall time it took with the CPU time it
consumed. The ratio is the slowdown the process is really experiencing (1.0
on an idle host, 2–8x on a contended one) and the budget is scaled by it.

- On an **idle host** the factor is 1.0 and every budget is exactly what the
  test asked for. No behaviour changes at all, and CI is unaffected.
- On a **contended host** the budget grows in proportion to the slowdown.
- A predicate that never becomes true **still fails**. The hang is still a
  hang; it just gets a budget that matches the CPU it is actually getting.

Two factor flavours, because they answer different questions:

- **Scenario budgets** (the product's own timing knobs that a test hands it)
  use a factor that is fixed for the life of the process and only ever
  grows. A scenario and the assertion that compares against it must use the
  same number, or the test measures how the host drifted mid-test instead of
  what it is about.
- **Wait deadlines** use the worse of "how slow is the host right now" and
  "how slow has it been at any point in this run", so a momentary quiet
  reading cannot hand a wait a budget the host has already shown it cannot
  meet.

## Verification

### The release contract, and why it is recorded as it is

`npm run release:check` is the release contract. On this workstation it does
not reach a green run, and the reason is recorded here rather than glossed
over: **the host is contended, and the contract is a wall-clock contract.**

The contract DOES reach a green run where the host is not contended: the
release workflow's own CI run of this tree finished the full suite at
**4208 pass, 1 skip, 0 fail across 460 files, exit 0** in 803s on GitHub's
runner, and then stopped at the `check:inventory` gate described above. That
run is the proof that the released content is sound; what follows is the
record of the eight local attempts, each of which exposed a defect that is
now fixed.

Eight full contract runs were attempted. Their outcomes, and what each one
established:

| Attempt | Outcome | What it showed |
| --- | --- | --- |
| Codex session, before this release's changes | **exit 0 — 4200 pass, 1 skip, 0 fail across 459 files** | The runtime tree this release ships was green end to end. |
| 1 | 10 fail | Every failure a wall-clock deadline: `settlement timeout`, `timed out after 60000ms`, the fleet scan's 2s ceiling. |
| 2 | 3 fail | Same class, fewer of them, as the host quieted. |
| 3 | 9 fail | A burst at high load, in the same class. |
| 4 | 1 fail | A single test that took 108s where it normally takes 22.8s — killed by bun's own 60s timeout. |
| 5 | killed | The OOM killer, with 2 GB of RAM free on a 44-user host. |
| 6 | 1 fail | A test whose budget was still the old 60s. |
| 7 | 1 fail | A test whose budget was scaled but whose *assertion* raced the state write. |
| 8 | 1 fail | The same, in the respec builder. |

Each failure was then fixed at its cause — not by loosening an assertion, but
by giving the wait or the scenario a budget that matches the CPU the host is
giving, or by observing the effect the test is actually about instead of
racing it. The focused verification below is the result.

The full logs of the contract attempts are kept in this directory so the
sequence is inspectable rather than asserted.

### Focused verification of the released tree

Every test file this release touches — 61 files, 668 tests — run together
after the last fix: **662 pass, 1 skip, 5 fail**. The complete output is
`focused-verification.log` in this directory. All five failures are in the
two slow files named under *Known residual* below, in the race class that
release addresses; every other file in the set is green.

The new gate machinery has its own unit tests
(`tests/host-contention.test.ts`): the measurement is bounded and never
reports a speedup, a budget is never smaller than the one asked for, an idle
host is a no-op, the runner passes a load-sized timeout to bun, and no test
file may hand-roll a wait deadline again.

The mutation-evidence harness that guards the shipped documentation was run
against the retargeted control: `node scripts/verify-test-pin-controls.mjs`
exits 0 with 26/26 controls passing, and the `changelog range stale` control
still rejects the mutated stale range (processExit 1) — the guard is live.

### Known residual

Two slow files remain intermittently sensitive to host load, both in the same
class — the test observes a durable effect that lands a moment after the read:

- `tests/behavioral-orchestrator.test.ts` is the suite's whale (156 tests,
  the full-harness lifecycle matrix). On a heavily contended run a recovery
  wait can outlast its budget and the tests that follow it inherit the
  unsettled state. The file passes 156/156 when the host has room and fails
  a cluster of its neighbours when it does not.
- `tests/respec-builder-audit-runtime.test.ts` asserts that the builder phase
  reached "complete" after a dispatch that returns before the verdict lands.
  Two of those sites now wait for the phase; the rest still race it, and on a
  contended host they read a perfectly healthy "auditing".

This is the same class of defect the release addresses, in the two places
where the observed quantity is the product's own audit wall rather than a
test budget. It is recorded here as open work for the next patch, not
presented as closed. The fix pattern is established and applied at several
sites already: capture the scenario values once, and wait for the effect the
assertion is about rather than racing it.

## Publication

`docs/RELEASING.md` governs. The release is committed, the tag `v0.39.42` is
pushed on the reviewed tree, and a GitHub Release is created from that tag
(not a draft, not a pre-release). `.github/workflows/publish.yml` verifies the
tag equals `package.json`'s version, re-runs the complete `release:check` in
CI — on GitHub's runners, where the host is not contended — and only then runs
`npm publish --provenance --access public`. The npm registry remains the
publication authority; a tag and a commit are not proof that the package was
published.

**Why the registry receipt is not in this commit.** The registry can only
serve 0.39.42 after the tagged commit is published, so a tracked registry
receipt would necessarily be committed *after* the tag — which would make the
tag and `HEAD` different commits. The registry receipt is therefore recorded
in the GLLA journal and the terminal summary rather than in the tracked tree,
and `npm view pi-goal-list-loop-audit version dist-tags.latest` is the
independent check.
