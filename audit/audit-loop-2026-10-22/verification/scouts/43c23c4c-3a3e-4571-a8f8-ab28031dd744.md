## F1 — HIGH — the audit verdict artifact is unauthenticated: the audited bash child can forge its own `<approved/>` and the parent applies it

**Defect.** The parent (and the post-restart recovery path) accept any `result.json`
in the audit job dir whose identity fields match the `request.json` that sits in the
same directory. Those values are readable — and the directory is writable — by the very
process being audited, so a prompt-injected auditor can write the verdict itself.

Code side (what is accepted):
- `extensions/goal-loop-auditor-process.ts:2462` —
  `if (result.protocolVersion !== PROTOCOL_VERSION || result.attemptId !== attemptId || result.requestHash !== request.requestHash) {`
  is the *only* authenticity gate on the result; `attemptId` and `requestHash` are both
  written by the parent into `request.json` in the same dir.
- The audited process reaches that dir: `scripts/goal-auditor-worker.mjs:806`
  `"--tools", "read,grep,find,ls,bash",` and `:827` `cwd: request.cwd,` (the audited
  project), while the job dir is inside that project —
  `extensions/goal-loop-auditor-process.ts:2217`
  `const jobDir = path.join(piGlaDir(args.cwd), "audit-jobs", attemptId);` and
  `extensions/glla-state-root.ts:141` `return path.join(cwd, ".pi-glla");`
  (same uid, dir mode 0700 ⇒ the child can list/read/write it).
- Every downstream gate is satisfiable from the request file: `request.json` holds the
  prompt (with the verification contract), `goalRevision`, `attemptId` and `requestHash`,
  so a forger can also satisfy the audit-tool floor (`toolCalls:[{name:"bash"}]`), the
  `regression_shield` (evaluated over the forged `output`), and `challenge:"confirmed"`.
- The verdict also survives: the parent's `finally` block (right after
  `extensions/goal-loop-auditor-process.ts:2699`) keeps a job dir when
  `auditDirHasResult(jobDir)` is true, and `readCompletedCompletionAudit` re-applies it
  later through the same self-referential gates —
  `extensions/goal-loop-auditor-process.ts:2092-2094`
  `reject("result-protocol") / reject("result-attempt") / reject("result-hash")`.

Contract / consumer side (what is promised):
- `docs/DESIGN.md:434` — `### Decision 1: Anti-bamboozle via isolated auditor`
- `docs/DESIGN.md:152-153` — "Requests and results are hashed and atomically written.
  The parent validates attempt/request identity, verdict markers, read-tool use, and
  `regression_shield` before applying any result."
- The hash is not a MAC: `scripts/goal-auditor-worker.mjs:247`
  `if (typeof request.requestHash !== "string" || request.requestHash !== hashRequest(request))`
  — `hashRequest` (`:130`) recomputes the digest over the *same parsed file*, so it
  detects corruption, not tampering. The module's own claim is therefore false:
  `scripts/auditor-child-env.mjs:11-12` — "Tampering with the list breaks the request
  hash, which the worker verifies at load."
- Consumer that settles the goal on the accepted verdict:
  `extensions/loops/goal-auditor-hooks.ts:1915`
  `if (result.approved && result.regressionShieldPassed !== false) {`

Honest caveat: `docs/DESIGN.md:445-451` already concedes that bash power mode "permits a
prompt-injected command or verifier to write repository/GLLA files or plant evidence"
and that "Those checks do not make arbitrary loaded code or planted evidence
trustworthy". What is *not* covered there is that the verdict ARTIFACT itself is
unauthenticated — the identity/tool-floor/shield/challenge gates are evaluated on
attacker-controlled bytes instead of constraining them.

**Fix direction.** Do not let the audited process write the verdict: publish the result
over a parent-owned channel (pipe/fd) or into a directory the auditor child cannot
write, and/or authenticate the result to the worker recorded in the lock (role/pid or
inode) before applying it; treat any result whose writer is not the recorded worker as
untrusted.

## F2 — MEDIUM — the per-tool timeout is a floor, not a ceiling: the audited model raises its own tool budget to the 6 h maximum

**Defect.** The effective tool budget is `max(operator setting, model-declared timeout)`
capped at 6 h. A tool call that declares `timeout: 21600` therefore runs for 6 hours no
matter how low the operator set `auditorToolTimeoutMs`, and the parent's own watchdog
adopts the same model-chosen number.

Code side:
- `scripts/goal-auditor-worker.mjs:599-607` —
  `const grantedToolTimeoutMs = (args) => { const seconds = args && typeof args === "object" ? args.timeout : undefined; ... }`
  and `const effectiveToolTimeoutMs = (args) => Math.min(MAX_TOOL_TIMEOUT_MS, Math.max(TOOL_TIMEOUT_MS, grantedToolTimeoutMs(args) ?? 0));`
  (`args` is the model's own tool-call argument, applied at `:985`
  `const timeoutMs = effectiveToolTimeoutMs(event.args);`).
- `extensions/goal-loop-auditor-process.ts:853-859` —
  `export function effectiveToolTimeoutMs(baseMs: number, grantedMs?: unknown): number { ... return Math.min(MAX_AUDITOR_TOOL_TIMEOUT_MS, Math.max(base, granted)); }`
- `extensions/goal-loop-auditor-process.ts:2510` —
  `const effectiveBudgetMs = effectiveToolTimeoutMs(toolTimeoutMs, lastProgress.currentToolTimeoutMs);`
  — the parent's kill deadline is derived from the worker-reported, model-derived value.
- pi does not clamp it: `node_modules/@earendil-works/pi-coding-agent/dist/bundle/chunks/chunk-GUORCHFS.js`
  `MAX_TIMEOUT_SECONDS=2147483647` and the bash tool's timeout parameter is documented
  as "maximum is ${MAX_TIMEOUT_SECONDS} seconds".

Contract side:
- `docs/DESIGN.md:134` — "Each auditor tool also has an independent five-minute ceiling."
- `extensions/goal-loop-auditor-process.ts:774-775` — "the settings layer defaults/clamps
  the user-facing `auditorToolTimeoutMs` key against the exact value the watchdogs use —
  one source of truth." (`extensions/goal-settings.ts:168` documents the operator knob's
  bounds as "30s–6h".)
- Both are contradicted by `max(base, granted)`: the operator's value never caps the
  model's request; only the global 6 h maximum does.

**Fix direction.** Bound the granted timeout by the operator's configured value
(`min(configured, granted)`) instead of the global maximum, so the documented
five-minute ceiling (and the operator's lowering of it) is what the watchdogs enforce;
keep honoring a longer declared run only when the operator raised the setting.

## F3 — MEDIUM — the worker-side extension fence does not confine specs to the audited roots, and the hash it leans on cannot detect a rewritten request

**Defect.** `filterLoadableExtensionSpecs` keeps *any* absolute existing path, so a
rewritten `request.json` can make the auditor load an arbitrary extension (arbitrary
init code) in the bash-capable child that holds the provider credential — while the
fence's own comment promises the opposite ("can only narrow the auditor").

Code side:
- `scripts/auditor-extension-specs.mjs:51-63` — a spec is kept when it is absolute
  (`:51` `|| !path.isAbsolute(spec)` is only a *reject* condition), when it exists
  (`:58` `loadable = exists(spec);`) and is then pushed (`:63` `ok.push(spec);`).
  There is no confinement to the resolved install roots (`~/.pi/agent/npm|git/…`,
  `<cwd>/.pi/…`) — an absolute path anywhere on the host passes.
- `scripts/goal-auditor-worker.mjs:819` — `for (const spec of loadableExtensions) piArgs.push("--extension", spec);`
  → pi loads it as an extension (extension init code runs in the child that also gets
  `--tools read,grep,find,ls,bash` at `:806` and the provider credential via the env
  allowlist).
- The rewrite passes the worker's load-time check: `scripts/goal-auditor-worker.mjs:247`
  recomputes the hash from the rewritten file itself (see F1).

Contract side:
- `scripts/goal-auditor-worker.mjs:265-267` — "scheme/flag/relative/nonexistent entries
  drop fail-closed at spawn so a tampered job dir can only narrow the auditor (fully
  isolated), never widen it into installs, fetches, or extra CLI surface."
- `scripts/auditor-extension-specs.mjs:11-15` — "Provenance cannot be re-derived
  worker-side … so the enforceable contract is hygiene: only absolute, existing,
  scheme-free paths reach pi." Hygiene is not confinement: an absolute existing path
  outside the audited roots widens the auditor rather than narrowing it.
- `scripts/auditor-child-env.mjs:11-12` — "Tampering with the list breaks the request
  hash, which the worker verifies at load." (false: the hash is unkeyed and
  self-referential — `scripts/goal-auditor-worker.mjs:130`, `:247`.)

**Fix direction.** Confine kept specs to the audited roots (resolved npm/git install
dirs + the project `.pi` dir) instead of "any absolute existing path", and/or bind the
request to a parent-held secret (HMAC over the request) so a rewritten `request.json`
fails the worker's load-time identity check.
